## I-10
**Kind:** candidate
**Statement:**
Verification of G-4 found the demo provider naming no recovery on an upstream failure.
Fixing that surfaced a larger defect underneath it, present since before contract-001 and
on the pushed branch: a tool throwing McpException produced no JSON-RPC response at all,
so the caller waited forever. Bisected by experiment — no filters, the logging filter
alone, the throttle alone, and two no-op filters all replied correctly; the logging filter
with any second call-tool filter beneath it did not. Not the number of registrations
(composing both into one behaved identically) and not the Serilog LogContext scopes.

Two things worth keeping from this. The first: the shallower defect masked the deeper one,
and fixing the shallow one made the product worse — the demo provider's errors moved from
an unhelpful reply to no reply, because they began throwing the exception type that hangs.
A fix that changes which failure mode a path takes has to be checked in the failure mode,
not only in the test.

The second: all 84 tests passed throughout. Every test for this guarantee exercised the
provider directly, and the defect lived in the server's filter composition, which no test
reached. A guarantee about what a client receives has to be tested from where a client
stands.

CORRECTED (2026-09-18): the defect this observation is built on does not exist.
The missing response was the measuring probe's own doing — it redirected the server's
standard error and never drained it, so the pipe filled and the server blocked. The
bisection that looked so clean was measuring how much each configuration logged, not how
it handled an exception. The second lesson above still holds; the first is void, because
the failure mode it describes was never real. Left as written, per the ledger's rule that
nothing is rewritten silently.
