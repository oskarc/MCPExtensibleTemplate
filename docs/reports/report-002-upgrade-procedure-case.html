The Upgrade That Lost Nothing

A first-hand case from an agent taking a live project from base-building-kit 0.16 to 0.25, with three days of records at stake. The procedure held — and the two numbers it grades itself by are not measuring where it costs.

0.16 → 0.25 (0d2f55a) One session, one pioneer, real records 2026-09-19
0records lost, verified line by line
3decisions asked of the pioneer
2real defects the rehearsal caught
7shortcomings found, all open

The verdict first, so the rest can be read against it: this is the most careful procedure in the kit, and it works. Nothing was lost, every check passed, the real run asked no question the sheet had not answered, and the whole thing was reversible at every point. What follows is not a complaint about that. It is the observation that the procedure is excellent at not losing things and has almost no machinery for doing things — and that the failure condition it grades itself against measures the pioneer's cost, not the agent's.

The corrected claim

C-1Corrected

The failure condition measures the wrong cost

ClaimedThe pioneer's recorded failure condition, carried on contract-007: “if it human is required to make many manual decisions or the agent needs to troubleshoot to make it work.” The rehearsal grades itself on exactly these — decisions asked, and troubleshooting steps.
Measured3 decisions. 0 troubleshooting steps. By its own instrument this upgrade was close to free.
Actual costThe upgrade section is 232 lines and 38,202 bytes, inside a skill of 74,252 bytes, and must be read in full before step 3 — which is itself the instruction (“read both kits in full”). It was read in four passes because it does not fit in one. Then steps 3–9 were executed twice, once on a copy and once for real, from prose, with no script for any of it. The dominant cost of this procedure is agent reading and hand-executed file operations, and neither number sees it.
Why it mattersBoth numbers were excellent and I skipped a required step (F-1 below). An instrument that reports a clean run while a step is being missed is measuring a proxy. The pioneer's condition is about their own experience, which is the right thing to protect — it was never meant to certify the agent's, and it is being read as if it does.

What held

V-1Verified

The rehearsal earns its cost twice over

It caught two things that would otherwise have reached the project:

A skipped header. I refreshed seven record headers and missed MAP.md. G3-retired.sh surfaced it on the copy. The real run refreshed eight and produced no note at all.

A near data-loss. P-010.sh sits in checks/ and is absent from the baseline, which makes it look like base-kit evidence. It is this project's own precedent check — P-010 is in this casebook, from a correction about a contract left half-implemented. The rule is written correctly; reading it correctly took a deliberate stop.

Neither would have been caught by any check on the real run alone. The rehearsal is the single most valuable step in the procedure.

V-2Verified

preflight refuses well, and says why

It refused twice: once on a raw clone (“a raw copy of the repository carries the kit's own records and must not be used”) and once on a dirty tree — a single telemetry.log the hooks had written during the session. The second message explains the reason rather than stating the rule: “your last commit is its snapshot and its way back.” That is the difference between a gate and an obstacle. It also correctly excludes kit-incoming/ and the rehearsal log from its own dirtiness test — a detail that could only have come from someone hitting it.

V-3Verified

Two orderings that are load-bearing, and documented as such

Checks before the bases are replaced. G3-retired exits 1 on the old template, which step 9 predicts and explains: once the base is replaced, a forgotten line reads as the pioneer's and passes as a note. Both halves were observed exactly as written.

The sheet before the run. The rehearsal produces every question with its default; the real run takes the answers and asks nothing. It asked nothing. For a pioneer who had corrected this agent twice in the same session for acting without an alignment moment, a procedure that concentrates every question into one presentation is the right shape.

V-4Verified

“Every figure comes from a command” is the best rule here

The rehearsal log must end with a table pairing each figure with the command that produced it. It changed how the work was done, not just how it was reported: it made “0 skills evolved” something computed rather than believed. This rule deserves to escape the upgrade procedure — it applies to any figure any kit agent puts in front of the pioneer.

Shortcomings

F-1Open

An enumeration by count, where a list was meant

Step 7 ends its migration list with:

The header comment block of every record follows the template rule — the six above,
and the learning log and the casebook …

Step 7 has exactly six bullets: CONTRACT-LOG, CORRECTIONS, LEDGER, DRIFTLOG, MANIFEST, MAP.md. So the sentence names eight files and requires the reader to count bullets to know which.

I read “the six above” as the YAML records, added the learning log and the casebook to reach seven, and dropped MAP.md because it is not a YAML and its bullet is about base entries rather than headers. An instruction that depends on the reader counting is one an agent will get wrong quietly. Name the eight files.

F-2Open

There is a script to build a release and none to install one

checks/ ships thirteen files — preflight, rollback, merge, residue, roots, hooks-selftest and five G* gates. There is no install.sh. Step 5 is prose describing file copies, and every agent writes its own loop.

Worse, it is written twice — once for the rehearsal, once for the real run — and nothing compares the two. The procedure's own safeguard is that the real run re-runs the same commands; but they are commands the agent composed, not commands the kit ships, so “the same” is on trust. The header loop I wrote for the rehearsal had the F-1 defect, and the only reason the real run differed is that a check caught it and I edited my own loop.

The kit now admits git and ships four new scripts. A install.sh <staged> <classification> that performs step 5 and is invoked identically by both runs would remove the largest remaining source of divergence.

F-3Open

A forgotten header degrades to a note, by design

Step 9 states the weakness plainly: once the shipped copy is replaced, “a forgotten line reads as the pioneer's and passes as a note.” On the rehearsal that note was the only signal that MAP.md had been skipped — and it came after the point where it could still fail the run.

So the detection of a missed step depends on a human or agent reading a passing check's note. In a run where nobody reads the note, the header silently keeps retired wording, and the next upgrade measures that wording as the pioneer's and asks about it forever.

F-4Open

The stale rule sits one clause from deleting a project's own work

The classification says the base kit's P-NNN.sh checks are its own precedents and do not travel — then qualifies, inside a 400-word paragraph, with “any P-NNN.sh check in checks/ whose precedent id is not in this project's casebook.”

The qualifier is correct and it is doing all the work. A project's own precedent check is indistinguishable by shape from the base kit's, absent from the baseline for the innocent reason that it was written after the last install, and destroyed by a single answer to the stale line. This is the only place in the procedure where the default motion is deletion of something the pioneer made. It should be a check, not a clause: refuse to list a P-NNN.sh as stale while its id is in the casebook.

F-5Open

The size guard measures paragraphs while the section grows

G5-steps.sh fails when a paragraph of the bootstrap skill exceeds 1,200 bytes — contract-016's answer to the text an agent follows while records are at risk. Measured on the installed 0.25:

longest paragraph in the upgrade section   1,068 bytes   ← passes
the upgrade section                       38,202 bytes
meta-bootstrap/SKILL.md                   74,252 bytes

Every paragraph is within budget and the section an agent must hold is 38 KB. The guard measures a proxy for readability and the total is unbounded — the same shape report-001 is about, in the kit's own size control. A budget on the section, or on the count of steps, would measure what contract-016 was actually protecting.

F-6Open

Nothing anywhere asks whether the upgrade improved anything

Every check verifies fidelity: nothing lost, structures intact, hooks behaving, the walk matching. Not one step asks whether the project can now do something it could not before.

This upgrade was perfect by every instrument the kit runs, and all five findings of report-001 survived it unchanged — the seal still blocks the write it depends on, the auditor's search is still unbounded, the walk's fixture still omits the real settings, the gate still never reads type, and nothing still detects a gate task that cannot complete. The adoption loop that has never once run in this project still cannot run.

An upgrade report that lists what was taken, ported, asked, removed and migrated can be entirely green while the thing the pioneer upgraded for is untouched. The what this did not check section is the right instinct; it is written by the same agent that just declared success, about the work it just did.

F-7Open

The log has no model of a non-contract entry

Continuing report-001 F-5. This upgrade's migration gave an analysis report the fields verification_state: legacy, audited: legacy, disappointment: legacy, premortem: legacy, red_test: legacy and cost: legacy — a pre-mortem and a red test on a document.

It is harmless only because stop-gate.sh keys on status, and the status had to be invented (published) since the enum has no value a report can honestly hold. meta-contract-artifact added reports to this log without the base schema, the migration list or the gate learning that they exist.

The mechanism, drawn

Five green checks, a clean walk, nothing lost — and the question of whether the upgrade changed anything the pioneer upgraded for is asked by no step.

What was not answered

QuestionWhy it stayed open
Would a different agent have executed step 5 the same way? Untestable from one run. The concern in F-2 is structural: the loop is composed, not shipped, so two runs can differ with nothing noticing. One data point — mine differed between rehearsal and real run, deliberately, because a check caught a defect.
Do the 11 walk states added since 0.16 cover any of report-001's findings? The walk passes against its own expected file; which states are new and what they assert was not read. settings.json and kit-sealed still appear nowhere in walk.sh, which bounds the answer but does not give it.
Do the new hooks behave as live events? hooks-selftest.sh runs each once against a throwaway copy. Live behaviour in a real session was not exercised; the root-finding wrapper is the change most likely to matter and was not seen firing from a subdirectory.
Is the rollback path real? rollback.sh was never invoked — the run did not stop. An untested way back is a way back on paper.
Does any of this hold on a project whose skills were edited? This project had zero residue, so merge.sh's three-way merge, its conflict output and the reapply/replace question were never exercised. The most intricate machinery in the procedure went untested by this case.

Verdict — judgement, not finding

The procedure is sound and I would not change its shape. Rehearse, present one sheet, run without asking, verify, report, and keep a way back — that is the right sequence, and it protected three days of irreplaceable records without a single anxious moment. The rehearsal and the figures-and-commands rule are the two best mechanisms in the kit.

Its weakness is a family resemblance: the procedure is prose that an agent performs, and the checks verify the result rather than the performance. Every shortcoming above is an instance — a list given as a count, an install step with no script, a missed header that degrades to a note, a deletion rule held back by one clause, a size guard on paragraphs, and no efficacy test at all.

In order of what each forecloses:

  1. Ship install.sh. Step 5 performed by a script both runs invoke identically. It removes F-1, F-2 and F-3 at once, because a named list in code cannot be miscounted and the two runs cannot diverge.
  2. Make the stale rule refuse. A P-NNN.sh whose id is in the project's casebook is never listed as stale — a check, not a clause. This is the only data-loss path in the procedure.
  3. Add one efficacy question to step 9's report. Not a check — a required section: what could this project not do before, that it can now? Answering “nothing material” is a fine answer and a true one for this upgrade. Leaving it unasked is how a green report gets read as progress.
  4. Budget the section, not the paragraph (F-5), and teach the log what a report is (F-7).

One thing to carry beyond the upgrade: “every figure that reaches the pioneer comes from a command” changed how this agent worked, not only how it wrote. It belongs in the foundation, not in one procedure.
