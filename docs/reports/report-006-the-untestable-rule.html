The Untestable Rule

The seal, and why it is not that they missed it

F-1Corrected

The settings template was edited in 0.29 — just not the part that matters

The pioneer's challenge was reasonable: templates/settings.template.json appears in contract-021's changed files, so the commits look like they addressed it. Diffed, the whole change is an addition:

+      {
+        "_kit": "base-building-kit",
+        "matcher": "Task|Agent",
+        "hooks": [ … agent-launch.sh … ]
+      }

The permissions block beneath it is untouched, at 0.24, 0.25, 0.27 and 0.29:

"permissions": { "deny": [ "Read(kit-sealed/**)" ], "additionalDirectories": [] }

A search of the kit's own contracts, reports and contract log finds no claim that the seal was addressed. This is not a fix that fell short. As far as the record shows, it has not been picked up.

F-2Open

The mechanism, restated precisely

The batch assembler is instructed, at step 6 of its own file: "Seal the key at .claude/kit-sealed/B-NNN.key". Its own write-scope.sh frontmatter lists kit-sealed/ among the three paths it may write. And the project's settings.json, installed from the kit's own template, denies that path — which refuses the Write tool, not only Read.

Its other route is closed by the kit itself: deny-paths.sh, in the same frontmatter, denies any Bash command whose text contains kit-sealed/.

So the agent is told to write a file it is forbidden to write, by two rules the kit ships, and it correctly refuses to work around either. No key, no batch. No batch, no decision reaches the pioneer. No decision, nothing reaches a skill — which is why this project holds 53 candidates, 8 of them due, and has adopted none across two completed contracts.

Every fixed finding lives somewhere the kit can read and test: bash, prose, a schema, an agent's instructions. The kit's entire verification apparatus is bash — the walk, the G* checks, the hooks selftest. It is very good at this, and it has been fast.

The seal is the only reported finding that lives in the interaction between a project's settings.json and the tool layer that enforces it. And that layer does not govern bash. A > redirect writes to kit-sealed/ without obstruction, because the deny rule constrains an agent's Write tool, not the filesystem. The kit's own Bash blocking comes from deny-paths.sh, a hook that only runs when an agent invokes Bash — not when walk.sh does.

So 0.29 giving the walk's fixture a settings.json changes nothing here. The fixture can now copy the permission rules in, and a bash test writing to the sealed path will still succeed, because nothing in that fixture is subject to them. Any test the kit could write for this bug would pass.

That is the argument. Not that the finding was overlooked, and not that the evidence was weak — but that it is the one finding whose truth the kit cannot establish by running anything. Every other finding in this series arrived with, or quickly acquired, something that fails. This one can only be established by reading the permission semantics and reasoning about them.

The kit fixes what it can test, quickly and well. The one finding outside that boundary has not moved in four releases, and it is the one holding every adoption in this project.

What this report does not establish

QuestionWhy it stayed open
Does a Read(…) deny really block the Write tool? Not reproduced first-hand. The evidence is the refusal message the blocked assembler reported: "File is covered by a Read deny rule in your permission settings and cannot be written." Reproducing it means attempting a sealed-path write, which the kit counts as drift and its auditor greps for. This is the weakest link in the chain and it has been the weakest link for four releases.
Is the fix a rule change, a path change, or a different guard? Not determined. Read-denied and write-allowed for one agent may not be expressible in that settings schema at all; moving the key outside the denied path and protecting it another way may be simpler. That is the maintainer's call, not this project's.
Does this affect projects that never reach a batch? Silent until the first batch. Every consumer project accumulates candidates from day one and meets this at the moment the standard would first move.
Are there other findings in the untestable layer? Only one has been found. The category is defined here from a single member, which is a weak basis for a category.
Would the maintainer have fixed it if a test existed? Unknowable. The correlation between "testable" and "fixed" is nine for nine and one for one against, on thirteen findings — suggestive, not proof of cause.

Recommendation — judgement, not finding

  1. Treat the seal as a reasoning defect, not a test gap. It will not appear in any run. The three facts that establish it are all readable without executing anything: the assembler is told to write kit-sealed/B-NNN.key; its write-scope.sh permits that path; the shipped settings.json denies it. Those three sentences are in the kit's own files and they contradict each other.
  2. Get a first-hand reproduction from a project that can afford it. A scratch project with no records to protect can attempt the write and report the refusal verbatim — which this project has declined to do for four releases because the attempt is drift. That single command is the missing evidence.
  3. Consider what else sits in that layer. Permission rules, tool availability, agent frontmatter scopes, the harness's own behaviour. The kit's tests cannot reach any of it, and it currently has no other way of knowing when something there is wrong.
  4. Fix G2 against contract-018 and register meta-understanding. Both are inside the testable boundary and both are live in this project right now.

What this says about the kit, which is mostly good. Nine findings fixed across four releases, several within hours of the report that named them, every one of them somewhere a test could fail. That is a working feedback loop and it is rare. The blind spot is precise and small: the layer the tests do not reach. Knowing the shape of it is worth more than the one bug, because that bug is now the only thing standing between two completed contracts and the first line this standard has ever learned.
