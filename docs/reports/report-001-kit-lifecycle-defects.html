Gate Tasks Nobody Can Clear

Three lifecycle steps in base-building-kit cannot be completed by the agents named to complete them. The kit's own lifecycle walk passes all 36 states while this is true, because its fixture omits the two things that break them.

Found against v0.24 (60c98eb) Re-checked at v0.25 (0d2f55a) — all five still open Observed in a project running v0.16 2026-09-19
5findings, all open in 0.24
1claim corrected
4gate tasks that could not complete in the field
0of 25 candidates adopted in 3 days of use

Re-checked at v0.25. Contract-017 landed between the first draft of this report and its publication, adding preflight.sh, rollback.sh, merge.sh and hooks-selftest.sh — real release machinery for install and upgrade. None of the five findings below is touched by it. Verified file by file against origin/main: the deny rule at settings.template.json:63 is unchanged, the auditor's step 1 is unchanged, and stop-gate.sh and walk.sh still contain zero occurrences of type and settings.json respectively. hooks-selftest.sh is the nearest thing to F-4, but it checks that each hook runs, not that the task a gate hands over can be completed.

All five were found by running the kit, not by reading it. The project where they surfaced has two contracts, 31 observations, 25 candidates, 16 corrections, 10 precedents and 7 drift entries — and zero lines of skill guidance changed since installation, because the adoption path has never executed once.

The corrected claim

meta-mechanisms/SKILL.md → Adding or changing a mechanism states the guarantee that the lifecycle walk provides. That guarantee does not hold.

C-1Corrected
Claimed“walk the lifecycle, not only the script — one batch and one contract through every state, because each hook can pass while the loop they form deadlocks. … a state the walk does not visit is a state nobody has seen.”
Actualwalk.sh exits 0 on all 36 states while two steps of that same loop cannot be completed by any agent. The walk drives stop-gate.sh and asserts what it says; it never runs the agent the gate names, so it cannot observe whether the handed-over task can finish.
Why it can't see itThe fixture supplies the broken step for free. walk.sh:59 is w_batch() { cat > "$K/meta-ledger/batches/$1.md"; } — batch files appear by fiat. The fixture builder (lines 28–35) writes the manifest, contract log, ledger, corrections, casebook, drift log, map and founding file, and no settings.json, no agents, no kit-sealed/. Line 420 asserts the gate names kit-batch-assembler; the assembler never runs.

Findings

F-1Open

The seal blocks the write the seal depends on

templates/settings.template.json:63 ships "deny": ["Read(kit-sealed/**)"]. The Write tool refuses a path covered by a Read deny, so kit-batch-assembler cannot write B-NNN.key. Its Bash route is closed by its own deny-paths.sh hook. Both routes shut.

The agent's frontmatter contradicts itself — the same file passes kit-sealed/ to write-scope.sh as a path it may write:

- matcher: "Edit|Write"
  … write-scope.sh "meta-ledger/batches/" "kit-sealed/" "meta-ledger/LEDGER.yaml"

meta-mechanisms/SKILL.md:88 reasons about this rule entirely in terms of reads — “applied to Grep and Glob on a best-effort basis”, “Bash can still read the directory”, and under What neither covers: “Bash reads”. Writing is never considered. The rule was written as a read restriction and behaves as a path restriction.

Field consequence. The assembler produced a correct B-001.md (11 real items), could not seal it, correctly refused to work around either guard, and deliberately left batches: [] so the blind would not arm on a batch whose key reveal-key.sh could never open. Its judgement was sound; the mechanism was not.

F-2Open

The auditor's search strategy is unbounded on its own input format

agents/kit-session-auditor.md:33 — “Transcripts are large: use Grep, not a whole-file Read.” On JSONL a record is a whole conversation turn, so a grep hit returns that entire turn. Measured on a 16,112,599-byte, 5,958-line transcript:

grep "contract-002"   304 hits   1,820,666 bytes   ← 11% of the file, one call
grep "implemented"    261 hits   1,910,328 bytes
grep "drift score"    118 hits     609,254 bytes
grep "Tier 1"          14 hits     312,202 bytes
longest single record            208,514 bytes
                                 ───────────
the four searches step 1 names:  ~4,650,000 bytes

Grep here is not cheaper than the whole-file read it replaces; it is a whole-file read with extra steps. The instruction guards against size by naming a cheaper tool, but the tool's unit of work is a line and this format's line is a turn.

The same agent succeeded on the same file when it was ~2,750 lines, writing a full audit. Three launches and two resumes at the current size produced nothing — no output, no error, ~240 tool calls. 0.24 adds the presented_for_pioneer check (contract-014), which does more work on the same unbounded input, against maxTurns: 30.

F-3Open

Turn budgets are uniform; contract size is not

kit-verifier (maxTurns: 40, unchanged 0.16 → 0.24) hit its limit at 51 tool uses against a four-tier contract with ~20 clauses, and delivered no report at all — it was still calling tools when it stopped. A budget that is exceeded mid-work produces silence, not a partial result, so the gate's task simply does not complete.

This is the same shape as F-2 at a different parameter: an agent whose input scales with the work, and a bound that does not.

F-4Open

Nothing detects a gate task that never completes

The kit already names this failure precisely, under Failure modes:

“A step nobody can clear. Every gate task must have a write that ends it. A task with no exit repeats every turn and blocks every step below it.”

Four were observed in one project in three days — the session audit, the batch seal, the verification, and adoption as their consequence. Each agent failed silently: no error, no partial write, nothing in telemetry distinguishing “ran and found nothing” from “could not run”. The only signal is a gate that hands over the same task indefinitely, which reads as nagging rather than as a defect. Over six consecutive turns in this session the gate re-issued one uncompletable task without any mechanism noticing.

F-5Open

A documented exemption that the gate does not implement

CONTRACT-LOG.template.yaml states the rule in its schema comment:

type: contract    # or analysis-report, with a report-NNN id; the gates skip those

stop-gate.sh never reads type. It selects by field position on status, verification_state and audited — '$2=="implemented" && $4=="false"' and its siblings. An analysis report registered with status: implemented therefore arms the audit gate and the verification gate for a document that has no session to audit and no clauses to verify.

Compounding it, meta-contract-artifact introduces report entries into this log but extends no status enum, so there is no lifecycle value a report can honestly carry. The five documented values all describe a contract's build cycle.

This one was found while registering this report in the log — the act of following the kit's own instruction surfaced the defect. It is the same shape as F-1 through F-3: a control that is written down and not implemented, discovered only by executing it.

The mechanism, drawn

The broken edge is the one the walk's fixture hands over for free. Everything left of it works; everything right of it has never run.

What was not answered

QuestionWhy it stayed open
Is Write-under-a-Read-deny documented Claude Code semantics, or version-specific? The refusal message was reported by the blocked subagent. It was not reproduced — attempting a sealed-path write in the main session would itself be the drift the kit audits for.
Does the auditor exhaust context at step 1, or later? Its inputs were measured, not its internal state. The byte counts prove the strategy is unbounded; they do not prove where it stops.
Are there defects in the other seven releases' worth of change? Three known defects were checked against 0.24. The kit was not reviewed.
Is w_batch() deliberate scope or oversight? A unit test of the gate's messages is a legitimate thing to have. Whether it was meant to also stand for the lifecycle guarantee is the author's to say.
Did the 0.24 upgrade rehearsal exercise any of this? Its report (report-004) was not read; only the kit tree was examined.

Recommendation — judgement, not finding

The three defects are one shape: a control checked in a configuration the running system never uses. Repairing them individually leaves the shape intact, so they are ordered by what each forecloses.

  1. Separate read-denial from write-denial on the seal. The assembler needs write-yes / read-no. Either express the project rule so Write does not inherit it, or move the key somewhere the deny does not cover and protect it by hook instead. Smallest change; unblocks adoption on its own.
  2. Bound every agent input that scales with the work. A digest step for the auditor — a script-produced, fixed-size artifact it reads instead of the raw transcript — and a turn budget for the verifier proportional to clause count rather than a constant.
  3. Extend the walk to run each gate task to completion under the real settings.json, by the agent the gate names. This is the one that matters: it would have caught all three, and it is what the kit's own text already claims the walk does. Keeping w_batch() as a fast path is fine, provided one pass goes the long way.
  4. Give a stalled gate task a signal. The same task handed over N times with no state change is currently indistinguishable from a patient backlog. It should say so.
  5. Make the gate read type, and give reports a status of their own (F-5) — or drop the “gates skip those” claim from the schema. Either resolves it; leaving the comment in place while the code ignores it is the failure the rest of this report is about.
