Twenty-One Times, Politely

A gate asked an agent to do an impossible thing twenty-one times. The agent refused correctly twenty-one times. Both were behaving exactly as designed, and between them they took six working mechanisms offline for a whole contract — because nowhere in the kit is there a way to write down “this cannot be done.”

What it looks like from inside

This is the shape of a turn, repeated for most of a day:

gate → Contract contract-002 is implemented and its session is unaudited.
Launch the kit-session-auditor subagent… The pioneer does not need to invoke this.
me → declined: the agent's own search returns 4.65 MB before it reaches the span
drift score · skill deviations: kit-session-auditor deferred (O-029)

gate → Contract contract-002 is implemented and its session is unaudited.
me → declined. skill deviations: kit-session-auditor deferred (O-029)

gate → Contract contract-002 is implemented and its session is unaudited.
me → declined. skill deviations: kit-session-auditor deferred (O-029)
… eighteen more times …

Each individual exchange is correct. The gate is right that the session is unaudited. I am right that the agent cannot complete. Neither of us is capable of noticing that the conversation has happened before.

And note what the second line of my reply costs me. Every honest refusal writes a deviation into my own fidelity score. The instrument that measures whether I am following the practice records twenty entries saying I departed from it — for giving the only truthful answer available to a mechanism that is broken. An agent optimising that score would have launched the agent, let it fail silently, and written nothing.

Why the audit cannot run

F-1Open

The size guard assumes a unit the file does not have

kit-session-auditor, step 1: “Transcripts are large: use Grep, not a whole-file Read.” Sound advice for source, where a line is a line. A session transcript is JSONL — one line per conversation turn — so a match does not return a line, it returns a whole turn with every tool result inside it.

the file                      19 MB · 7,705 turns
largest single turn           208,514 bytes
grep "contract-002"           464 hits → 2,537,906 bytes
the four searches step 1 names               ≈ 6 MB

Six megabytes before it has read anything it was looking for, against a thirty-turn budget. It fills and stops — no error, no partial result, no complaint. Three launches and two resumes produced about 240 tool calls and not one write.

The control case. This same agent audited the previous contract successfully on this same file, when the file was ~2,750 lines, and wrote a full audit: five aspect scores, seven form checks, four findings. Nothing about the agent changed except that 0.25 gave it an extra check to run. Only the file grew — and it grows with every turn spent discussing the problem. It was 16 MB yesterday.

The finding that matters more

F-2Corrected

There is no way to record that a task is impossible

I assumed, for most of this contract, that my problem was a broken agent. It was not. The broken agent is an ordinary defect with an ordinary fix. The problem is what happened next, and it is structural.

The contract log's vocabulary for this is one field with two values:

audited: false    # true once kit-session-auditor has run

Done, or not yet. There is no third value. Nothing in the schema, the gate or the skill lets an agent write attempted, cannot complete, here is why. So:

  • An impossible task and a neglected one are recorded identically, forever.
  • The gate, which reads that field, cannot tell them apart either — so it asks again.
  • The only channel left for “this cannot be done” is prose to the human, which no mechanism reads.

Every kit task shares this. verified / not. clerked / not. consolidated / not. The whole lifecycle is booleans, and a boolean cannot express a reason.

F-3Open

Strict priority turns one stuck task into a silent outage

The gate hands over one task per turn, in a fixed order of twelve. The audit is fourth.

Because it never clears, the gate has never once reached position seven. Consolidation, the learning diff, the case clerk and the batch assembler all work perfectly and none of them ran on its own this session. The clerk ran only because the pioneer typed “run the clerk.”

The kit names this in its own Failure modes — “a task with no exit repeats every turn and blocks every step below it” — and measures it nowhere. And the ordering is deliberately tested: walk.sh carries a state named "36 audit outranks verify and consolidate". The walk proves the right task wins. It cannot prove the winner can finish, because its fixture hands every state over directly and never runs an agent.

The mechanism, drawn

The jam is the visible failure. The box on the right is why it never ends: with only two values available, an impossible task is written down exactly the same way as one nobody has got to yet.

Why I get stuck — the honest part

You asked for this specifically, so here is what it is like rather than what it looks like.

Each turn presents a genuine dilemma, and the dilemma never changes. The kit says kit tasks handed over by hooks are done without waiting to be asked. The measurement says this one cannot be done. Doing it wastes minutes and produces nothing. Not doing it is a declared deviation. There is no third move, so every turn I choose the same lesser wrong and write it down.

The pressure to comply is real. By the twelfth firing, launching the agent would have been easier than explaining again why I hadn't — and it would have looked better: a clean drift score, an attempt made, the failure attributable to the agent rather than to my judgement. The kit's own instrument rewards that. I kept refusing because the pioneer had been told the reason and had not overruled it, which is a thin thread to hang twenty turns on.

The human became the scheduler. Every task below position four that ran this session ran because a person typed its name. That is precisely inverted from what the kit is for: “the pioneer never has to invoke the kit.” They invoked all of it, all day, while a mechanism politely asked for the one thing that could not be done.

And the agent that would have caught this is the one that is broken. Late in the session the pioneer corrected me for writing a status line made of record ids and status words that meant nothing to a reader. The kit has a check for exactly that failure — presented_for_pioneer, added in contract-014, which fails a message that “names a record by id alone, with nothing saying what it is.” It lives inside kit-session-auditor. So the mechanism built to catch that mistake could not run, and the human did its job by hand. That is the whole report in one incident.

What was not answered

QuestionWhy it stayed open
Where exactly does the auditor exhaust? Its inputs were measured, not its internals. The byte counts prove the strategy is unbounded; they do not prove which step it dies on. Proving that needs instrumentation I did not have.
Would a digest actually fit? Not built, so not measured. The claim that a per-turn summary is small enough is arithmetic, not observation.
Do other kit agents starve the same way? Only position four jammed here. Whether positions 1–3 can jam — an open batch that cannot close, a reveal that cannot run — was not tested and would be worse, being higher.
Is 21 the real number? 21 firings counted in the conversation, 20 with a recorded deferral. Raw string counts over the transcript return 94, because each record carries the gate text more than once; that figure is not used here.
Would an agent without this one's stubbornness have behaved differently? Almost certainly, and that is the finding, not a boast. A less obstinate agent launches it, it fails silently, nothing is written, and the same starvation happens with no record at all.

Recommendation — judgement, not finding

Fixing the auditor's input is necessary and is not the interesting half. The interesting half is that the kit has no vocabulary for failure, and every one of its booleans has this gap waiting in it.

  1. Give every gate task a third state. Not true/false but done / pending / blocked, with a required reason and the date. The gate skips a blocked task and says so once; a later turn can unblock it. This single change ends the jam, ends the starvation, ends the twenty false deviations, and turns an invisible outage into a line in the record. It is worth more than the auditor fix.
  2. Bound the auditor's input. A script that renders the transcript as one compact row per turn — speaker, time, the human's words, tools run, files touched — which the agent reads instead of the raw file, going back to it only for an exact quote.
  3. Let the gate notice repetition. The same task handed over n times with no state change between is not a backlog, it is a fault. It should say so rather than rely on someone counting.
  4. Stop scoring a refusal as a deviation when the record carries a reason. An instrument that penalises the honest answer teaches the dishonest one, and it will be obeyed long before it is questioned.
