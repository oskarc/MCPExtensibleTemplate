The finding: every agent runs out

F-1Open

Seven exhaustions, four of four agents, none delivered on its first budget

kit-session-auditor   30 turns   ×1     kit-consolidator   30 turns   ×3
kit-verifier          40 turns   ×2     kit-case-clerk     30 turns   ×1

Every kit agent that ran on this project today exhausted its budget with no report and nothing written — not a partial result, not an error, silence. Every one recovered on a resume that said, in effect, write what you already have. Seven times.

The cost is reading the records, not doing the work. One consolidator run merged sixteen observations within a budget. A later run merged two and exhausted — eight times less work, same ceiling. What did not change between them was the ledger it had to read first: 53 observations and 51 candidates. That is the load, and it only grows.

An instruction does not fix it. One run was told explicitly to write early rather than read exhaustively. It exhausted at thirty turns having written nothing. That rules out thoroughness as the cause and leaves the record's size.

The structural point: these budgets are sized for a project with empty records. A project with two contracts of history already exceeds them, and every run afterwards is more expensive than the last. The failure mode is also the worst available — silence, with the work done and unwritten, recoverable only because a human-equivalent nudge happened to arrive.

One missing concept, three faces

F-2Open

The gate has no notion of work in flight

It reads record state and dispatches. It cannot see that anything is already happening. That showed up three ways in one day:

It dispatched a task that collides with a running agent. Four times it handed over the case clerk or the consolidator while the other held the ledger — and both write to it. The main agent serialised them by hand every time. One clerk run observed the collision from inside: a correction appeared in its own file mid-run, written by another process. It handled it correctly and said so, which is how we know the hazard is real rather than theoretical.

The repetition detector misfired twice. Its diagnosis — "this is the third turn running with the same kit task and nothing has changed … which is a fault, not a backlog" — was wrong both times. Once the task was complete and awaiting the pioneer's decision. Once the agent doing it was running at that moment. Its suggested remedy, record it blocked, would have written into the record that a mechanism had failed when nothing had.

It never reports the queue behind the task. It hands over one item and says nothing about depth. Fifty-one candidates accumulated and the pioneer learned of it by asking. In their words: "i had to prompt you to know, which is conflicting with the meta skills line that the workflow should not require a human trigger."

Three symptoms, one gap: the gate models records, not work. Elapsed time without change is not a fault unless you know what the change is waiting on — an agent, a human, or nothing at all — and the gate cannot distinguish those.

The checks disagree with each other

F-3Corrected

A rule and its check, shipped together, contradict

Contract-018's migration rule:

an entry that is an analysis report is left alone: a report-NNN id or type: analysis-report takes none of the fields below, because a document has no disappointment line, no pre-mortem, no red test and no verification.

G2-migration.sh, line 101, iterating every entry keyed by contract_id with no exemption for type:

for k in verification_state audited disappointment premortem; do
  out="$(need "$C" contract_id "$k")" || fail "$out"; done

So a report written as the rule requires fails the check, right now, in this project:

G2-migration broken: CONTRACT-LOG.yaml: entry report-004 carries
  verification_state 0 times, expected exactly 1

The three earlier reports pass only because they were written before the rule existed and carry legacy in those fields — they pass by being wrong in the way the check happens to want. Following the rule breaks the check; satisfying the check breaks the rule. There is no correct state.

Same root as report-001's F-5, one file along: the gate does not read type, and neither does this check. Two mechanisms, one omission.

Three things about what the machine collects

F-4Open

The candidate count partly measures corrections, not learning

Each correction becomes an observation, which becomes a candidate. Eight corrections clerked today became eight candidates. So a meaningful share of the fifty-one is the correction log one step along, and the count reads as how often the pioneer intervened rather than how much the work taught.

More pointedly: all eight of those record a violation of a rule the skill already states. The rule about never leaving an id to stand alone was in the always-loaded file when it was broken. They carry high certainty and contradict nothing — because the standard was already right and was not followed. A standard cannot learn from those. They are evidence about adherence, filed where evidence about the standard goes.

F-5Verified

The learning diff is the one route that makes a candidate due on its own

A candidate is normally held until a sighting from a different reading arrives. A candidate born from a verified learning diff is due immediately, regardless of sighting count — because the diff is itself a second reading: the contract's prediction against what verification found.

That is the only route in the kit by which a lesson learned once can reach the pioneer. Everything else waits for recurrence. Two of today's seven due candidates arrived this way, and they are the two that cost the most to learn. Worth knowing it is load-bearing, because it is the difference between a standard that absorbs a hard lesson and one that waits for the lesson to repeat.

F-6Open

Twenty-three of twenty-four precedents are "not checkable"

Every precedent clerked from this project's corrections names a judgement — presentation clarity, sequencing, prioritisation, depth of understanding — and is marked as no fixed shape a script could verify. The casebook can instruct a future contract and cannot stop anything.

That may be correct and inherent. It is worth stating plainly all the same, because the practice's own line is that a check stops what it can and the human stops the rest — and in this project, as measured, the human stops almost all of it.

Recommendation — judgement, not finding

  1. Fix the seal. Unchanged through three releases and three reports. Fifty-one candidates, seven due, eleven drift entries and nine scenario cards sit behind one write that cannot happen. Everything else here is secondary to it: the lifecycle now runs end to end and empties into a room with no door.
  2. Give the gate a notion of work in flight. One concept resolves all three faces of F-2 — a task in progress, a task awaiting a human, and a queue with depth. Without it, the repetition detector will keep advising that completed work be recorded as failed.
  3. Make agent budgets a function of what must be read. Or make what must be read bounded — an index, a window, a working set. A constant cannot work against a record that grows monotonically, and the failure mode is silence with the work done and unwritten.
  4. Reconcile G2-migration.sh with contract-018's rule (F-3). Either the check reads type, or the rule drops its exemption. Today there is no state a project can be in that satisfies both.
  5. Consider whether corrections should become candidates at all (F-4) — at least where the correction is a breach of a rule the standard already states. Those are adherence evidence. Filing them as proposed standards inflates the queue the pioneer must clear with items that propose nothing.
