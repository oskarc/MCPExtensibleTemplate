Governed Requests

Resources and prompts answer any signed-in caller, unknown arguments pass silently, and a provider could switch the frame off — this contract makes every request pass a policy the provider cannot remove.

Direction

After this contract, a request reaches a provider only if a policy declared for that provider allows that caller, that kind of request and that shape of arguments; the server refuses to start if any tool, resource or prompt lacks a policy, if the frame's own parts have been altered, or if a governed setting is unknown; and any request kind nobody governs is refused. The bet is that one declared policy per provider, enforced by a frame providers cannot remove and that the tests and the real server both run, closes the ways in that Phase 1 left open - while what an argument's value means stays the provider's responsibility, stated as such.

The bearing. If it and the tiers disagree, the bearing wins.

What the pioneer locked

A clause that cannot be traced to one of these is wrong, not merely debatable.

  • Two contracts: every incoming request first, every outbound call second.
  • Every request kind governed, and any kind not governed refused.
  • Limits held in Redis now, required in production.
  • The confirmation gate for irreversible tools built now.

Tier 1 — who it is for

Who: an organisation's platform team running the server centrally, the teams whose tools it
exposes, the security function, and people calling tools through AI clients.
What they want: to add a provider by declaring what it may do, and to trust that nothing
undeclared gets through, even from a provider that does not cooperate.
Success: the platform team reads a provider's policy plus its validated configuration and knows
who may reach what, through which request kinds, with which argument shapes, at what rate. A
mistake or a typo stops startup instead of opening access. A refused caller is told which rule
refused them and what to do.
What it does not promise: that an argument's value is sensible for the provider (that is the
provider's code); that a person rather than their AI client approved an irreversible action (the
server enforces the round-trip; the client decides who answers); that a write came from someone
who just signed in (the gate bounds how long a revoked user keeps write access).
Cost today: resources and prompts are open to any signed-in caller; unknown arguments pass
silently; the only limit is per tool, shared by everyone, and per instance; nothing distinguishes a
destructive tool from a reading one.

Tier 2 — use cases

UC-1Declaring a provider: one policy covers every tool, resource and prompt, and the server starts. Edge: missing or orphaned policy, scope nobody can issue, wildcard or IP host, contradictory timeouts, labels not matching risk, configured upstream outside declared hosts - each refuses startup saying what and how to fix.
UC-2Listing: a caller sees only what their identity provider and scopes allow.
UC-3Using: tool calls, resource reads, prompt requests and completions are checked in a fixed order; a refusal names the rule and what to do. Naming something hidden is refused exactly as if it had been listed.
UC-4Argument shape: undeclared names, wrong types, over-long strings and non-numbers are refused before the tool runs; nothing reaches the upstream. Within the declared shape, meaning is the provider's.
UC-5Ungoverned request kinds are refused.
UC-6Write tools refuse a token issued more than 5 minutes ago. Purpose: a revoked user loses write access within 5 minutes. Decided: the Development-only local principal counts as fresh.
UC-7Irreversible tools require a confirmation tied to the exact arguments, valid 120 s, usable once. Different arguments, expired, altered, replayed, or a client that cannot confirm - all refused. The token must be under 60 s old (decided, overturnable: the roadmap's reading when an identity provider offers no introspection).
UC-8Limits per caller and per caller per tool hold across instances; with Redis unreachable, requests are refused.
UC-9Production loads only providers listed as enabled; the demo provider is not listed; an unknown name refuses startup.
UC-10In the sections the frame governs (identity, providers, limits, confirmation), any key it does not know refuses startup - typos and retired settings such as the old per-tool throttle.
UC-11Output over a tool's cap is refused with the cap named, not truncated. Injection detection in outputs is left to Phase 4, where its signal is consumed.
UC-12A provider that removes, replaces or adds to the frame's parts, or registers a tool through a side door, refuses startup naming the provider.

Boundaries

  • Outbound calls — hosts, redirects, internal addresses, response size, token forwarding, provider concurrency and daily budget — are the second contract. This one only declares the allowances and checks them at startup.
  • The audit pipeline is Phase 3; this contract logs a named event per refusal, not the chained audit record.
  • Strikes, suspension and revocation are Phase 4, as is injection detection in outputs.
  • What an argument’s value means for a provider is the provider’s, not the frame’s.

The gate

Approval authorises building exactly these clauses. A deviation found in flight stops the work and is put to the pioneer; it is not resolved quietly. After the build one guarantee is broken on purpose and the test that goes red is recorded before the contract reads implemented.
