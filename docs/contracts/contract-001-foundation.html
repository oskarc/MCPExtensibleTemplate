Phase 0 — Foundation

Six of this server's tools answer with empty records and report success; running it for an IDE opens a network port that serves nothing; a crash exits as if all were well. This contract makes the base tell the truth before a security frame is built on it.

Bearing

This contract makes the base governable: after it, a defect in this server fails a build instead of reaching a user, and the platform under the frame is current and honest about failure. The bet is that the frame the founding statement calls the core cannot hold integrity on a base where six tools silently return empty data and stdio opens a port nobody asked for.

Provenance

Everything below traces to one of these. A clause that cannot be traced to them is wrong, not merely debatable.

This application is a general purpose MCP server, it can be used by a small dev team or and big organisation looking to centralize MCP usage across the organisation. The app must be compliant with OWASP MCP Top 10 and other frameworks or approaches regulating secure usage of the protocol.

The core of the application is the frame that governs the providers, it must actually hold the integrity over time, making sure there are no loopholes or workarounds.

Tier 1 — Who this serves

Two users. The teams who will run this server — a dev team, or an organisation centralising MCP access. And, because this contract is foundational, whoever builds the later phases on it.

Success. The server starts only the way it was configured to start. Every tool returns real data or an error that says what to do. A broken change fails a build before anyone runs it. The runtime still receives security updates.

The cost of skipping it. Six tools return empty values and report success. Running for an IDE opens a port that serves nothing. A crash exits 0, so a supervisor believes the process is healthy. .NET 8 stops receiving security updates on 10 November 2026. Nothing runs on push, so all of it can return silently.

Tier 4 — How we would know

The pioneer authored the disappointment — "same as it reads" for all twelve — and the commands below are mine. Each says what failure looks like before it says what runs.

IdHoldsWhat is checked, and what counts as failure
T-1G-1Start over stdio in Development and inspect the process's listening sockets. Fails if any listener exists, or no JSON-RPC reply reaches stdout.
T-2G-1Start over stdio with the environment set to Production. Fails if the exit code is anything but 78, or the process serves a request.
T-3G-2Start with an invalid provider URL, then force an unhandled startup failure. Fails if either exits 0; expected 78 and 70.
T-4G-3Send a foreign Host header; then call 100 invented tool names and read the throttle's key set. Fails if the host request reaches authentication, or the key set holds anything but registered tool names.
T-5G-4Feed the demo provider a recorded camelCase payload and call all six tools. Fails if any returns an id of 0, an empty title, or an empty collection reported as success. Then return HTTP 500: fails if the error does not name a recovery.
T-6G-5Run every registered tool against a recorded response. Fails if any tool is registered with no path to success — specifically the climate tool, while its upstream serves only CSV.
T-7G-6Assert the timeout arithmetic at startup, then stall a fake upstream past the attempt timeout and count attempts. Fails if the assertion does not hold, or fewer attempts are made than configured.
T-8G-7Start with a handler that records calls, then probe both endpoints. Fails if either does not return 200, or a call was recorded before the first request.
T-9G-8Build the solution with warnings as errors; read both project files and package versions; search for suppressions around SDK deprecations. Fails on a build error, a project not on net10.0, packages not on 2.2.0, or a deprecation silenced rather than resolved.
T-10G-9Run the workflow's own steps against three seeded fixtures. Fails if any of the three passes.
T-11G-10Scan the tree for secrets and read every settings file. Fails if the scan reports anything, or an API key value sits in configuration.
T-12G-11Enumerate registered tool names and search the docs for each. Fails if a documented name does not exist, or a PascalCase spelling appears.
T-13G-12Check the tree is clean and the head commit exists on the remote branch. Fails if either is untrue.

Untested — three guarantees no test reaches

  • G-3's full middleware order. T-4 proves the host check precedes authentication, not the position of every stage. The rest is verified by reading.
  • G-2's exit code 70. Forcing a genuinely unhandled failure deterministically may not be possible. If it isn't, that half of T-3 becomes a reading check and the contract will say so.
  • G-8's "resolved rather than suppressed". T-9 catches the two common suppressions; a deprecation avoided some other way would pass.

Boundaries

This contract is foundation only. Naming what it excludes is what lets scope be refused later without renegotiating:

  • No identity. Callers are not authenticated; that is Phase 1.
  • No provider policy frame, no egress guard. The core the founding statement names is Phase 2, and it needs an identity to key policy on.
  • No audit trail, no strikes, no revocation. Phases 3 and 4.
  • No bounded response reads, no Redis, no container work. Phases 2 and 6.
  • The API key middleware stays for now. It is removed in Phase 1, when something replaces it.

The gate

Approval authorises implementation of exactly these twelve guardrails, verified by these thirteen tests, on the epic/security-hardening branch.

A deviation found in flight stops the work. If implementation cannot proceed against a clause as written, the work halts and the deviation is surfaced before anything else is done. An unauthorised deviation is drift, not a revision, and is recorded as such.

A change is a whole redraw. Not a patched clause here and a republished section there — the contract is drawn again in full, and this page is republished whole to the same URL.

One decision is deliberately open open — G-5: whether the climate tool is removed or rebuilt against the CSV endpoint. Approving as-is leaves that choice to implementation, on the condition that no tool remains which cannot succeed. That condition is what T-6 checks either way.

Before code: one guarantee is broken on purpose — G-4, by restoring the old case-sensitive deserialisation — and T-5 is seen to go red. A suite that has never failed carries no information.
