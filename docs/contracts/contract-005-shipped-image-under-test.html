Direction

After this contract, the thing that ships is the thing under test: the server image built from the repository’s Dockerfile. It runs on its own network behind a TLS front, against a real identity provider over HTTPS, test issuers, Redis and recording fakes of its upstreams. The tests see it only as a client and an operator would: through its network edges, its logs and its exit codes. contract-003’s end-to-end clauses run on it as written, and the five defects this environment found on arrival are fixed, each seen failing first. The bet is that four named extension points let egress, audit, guardrails, hardening and compliance each add their part without rebuilding the core: start a server with a settings delta, the upstream registry, the issuer registry and the network constant.

Choices made at the draw, approved as made

None of these stopped the work. Each was made with its reason and put to the pioneer at the gate; the contract was approved with them.

ChoiceWhy

Tier 1 — who it is for

Who: the teams adopting and maintaining the template, an organisation's platform and security
functions who deploy the image, and the pioneer judging whether the frame holds.
What they want: to know that the artifact they deploy - not an in-process imitation - holds the
frame against real clients, real tokens and real upstreams, and keeps holding it as phases add to it.
Success: the guarantees in the coverage table below are proven on the image, and each one that is
not is named there with its reason. A standard OAuth client connects to https://host/mcp as the docs
say. The documented deployment runs as written. A defect in the running program fails a test before
it ships.
What it does not promise: that a real person's browser login works (Phase 4); how the egress guard
will treat the identity provider's own traffic (the egress contract); IPv6 networking; a hardened
image (Phase 6).
Cost today: the shipped program has never accepted a token in a test; a standard OAuth client cannot
connect as documented; five defects were invisible to all 262 tests.

Tier 3 — guardrails

G-1 challenge(UC-1, 10, 11) A Dockerfile and a .dockerignore at the repository root; the ignore file excludes **/bin, **/obj, **/logs, .claude/, .git and docs/. The build is multi-stage. The SDK image matches global.json, the runtime is aspnet:10.0-noble-chiseled, and both are pinned by their multi-arch index digest. The container runs non-root (user 1654) with WORKDIR /app and a log directory the app user can write to. There is no test stage and no test material. Further hardening belongs to Phase 6.
G-2 as drawn(UC-2–11) A new project, McpServerTemplate.E2E (xUnit, in the solution, with its own lock file). It has no ProjectReference to the product or the test host, and sees them only through their network edges, logs and exit codes.
G-3 challenge(UC-3–6) A new library, McpServerTemplate.Testing, holding the token minting: TestIdentityProvider moves here from the fast suite, and both suites use it. It also holds a test PKI generated when a run starts: one CA plus leaf certificates covering every host name the environment serves. The key material lives in a temporary directory outside the repository, is mounted read-only, and is deleted after the run. Nothing of it is committed.
G-4 challenge(UC-1–10) One user-defined Docker network per run, with its IPv4 subnet a slice of 198.51.100.0/24, held in one harness constant. The front and the proxies get static addresses. The slice lies outside P2.7’s list as the roadmap states it today. Which ranges the egress guard blocks is the egress contract’s decision, and no test-only relaxation of address checking is allowed.
G-5 challenge(UC-1, 2, 5, 6, 7, 9) Keycloak 26.7.4, pinned by digest, run through the generic container builder in start mode. It serves HTTPS with a test-CA leaf, with its hostname pinned to https://keycloak.e2e.test:8443. One realm is imported, with a client-credentials client per test class, an audience mapper equal to Authentication:Resource and an explicit basic scope. It starts once per run and is shared by every test class.
G-6 challenge(UC-2–5, 7) A test issuer: a test-only container built from McpServerTemplate.TestIssuer (a small web project over the Testing library). It sits on the network under two issuer names, idp-a.e2e.test and idp-b.e2e.test, and serves each one:
• discovery and JWKS, counting every request per name
• an authorization-code endpoint: RFC 8414 metadata advertising S256; an auto-approving /authorize that returns code, state and iss; a /token that checks PKCE and mints the audience from the resource parameter
• an admin endpoint the test uses to mint tokens Keycloak will not (wrong audience, expired, alg none, HS256, cross-signed, missing claims, stale iat).
Its keys are generated when the container starts and never leave it. The test reaches it under the same names the server uses, through a name map in its HTTP client that validates TLS against the test CA. Placement chosen: its own container rather than a host port exposed into the network, so both platforms use the same mechanism and no SSH sidecar is needed.
G-7 challenge(UC-2, 6, 8) Upstream fakes behind an upstream registry, in which each upstream host name belongs to exactly one container. One WireMock (sheyenrath/wiremock.net-alpine, pinned by digest) serves opendata-download-metfcst.smhi.se, opendata-download-metobs.smhi.se and jsonplaceholder.typicode.com over HTTPS with a test-CA leaf. It also answers on a neutral alias, wiremock.e2e.test. Its journal is read through its admin REST API with a plain HttpClient, with no WireMock client package.
G-8 challenge(UC-1–11) The server under test.
• Build: built with the Testcontainers Dockerfile builder, tagged by a hash of the whole build context as .dockerignore filters it, and reused only while that hash is unchanged. A revision label is checked against the checkout before any test runs.
• Configuration: environment only, through one harness entry point, start a server with a settings delta. An unknown key in a delta fails the server’s own startup check.
• Trust: SSL_CERT_FILE and SSL_CERT_DIR both point at the test CA only, so a call to a host with no fake fails TLS instead of reaching the internet.
• Transport: BindAddress is 0.0.0.0, AllowedHosts is mcp.e2e.test only, and KnownProxies is the front’s address only.
• Running: stderr is captured, and the server counts as ready when /readyz answers directly, not through the front. There is one server container per test class, so counts never leak between classes; UC-7 starts two.
G-9 challenge(UC-1, 4, 7, 9, 11) A TLS front: nginx, pinned by digest, at a static address, holding a test-CA leaf for mcp.e2e.test. It terminates TLS, keeps the Host header, sets X-Forwarded-Proto: https, and sets X-Forwarded-For to the client address the test names in a test-only header. That header is a declared harness device standing for many clients behind one proxy, and the product trusts the address only because it arrives from KnownProxies. Every client-facing test dials https://mcp.e2e.test through the front.
G-10 challenge(UC-8) The test host is a separate project, McpServerTemplate.E2EHost. It composes the public AddHttpServer and UseHttpServer with the built-in providers plus test modules, which are defined only there:
• an irreversible tool whose every run sends one request carrying a unique marker to wiremock.e2e.test, a witness outside its own process
• a prompt provider that offers completions.
It has its own image name (mcp-e2e-testhost) and a test-only label. Containment does not depend on the environment name: the test host refuses to start (exit code 78) unless Authentication:Resource and every identity provider’s Authority and Issuer are hosts under .test, checked on the fully built configuration. It runs in Production with Redis, and it never passes configureIdentityForTests. The product project has no ProjectReference at all, and no workflow pushes any image.
G-11 challenge(UC-2–11) Harness discipline.
• Sabotage: every end-to-end test has a named sabotage that acts only in the E2E fixture (its inputs, container environment or network) and weakens one thing for one test. Its recorded red fails on the assertion that carries the test’s claim, and the failure message is recorded with it. A red at a self-check, a positive control or startup does not count. CI fails if MCP_E2E_SABOTAGE is set.
• Absence: asserting that nothing happened is legal only on a witness that recorded something earlier in the same test, and whose cache, if it has one, was cold when the absence was checked.
• Expected sets: the served tools, resources, prompts and governed request kinds come from the image’s own startup line, which gains the request kinds. The fast suite’s rule matrices remain the independent check on that line.
• Self-checks: the fixture’s self-checks name the phase and the cause of an environment fault.
G-12 challenge(UC-11) The five fixes. Each lands only after its end-to-end test has been seen red on the current code.
(1) MCP answers at /mcp. Startup refuses (78, naming Authentication:Resource) when the Resource’s path, with a trailing slash trimmed, is not /mcp. The URL named in the challenge and RFC 9728’s well-known location for that resource both answer with the same document. Docs and test constants are updated.
(2) Startup refuses (78, naming the key) when a non-loopback BindAddress has no AllowedHosts, or when any AllowedHosts entry is *, 0.0.0.0, [::] or ::. HttpTransport joins the sections the settings allowlist governs.
(3) ClientIdClaim is applied, so the claim it names is the one a token must carry. A value that is a registered JWT claim (iss, sub, aud, exp, nbf, iat, jti) or equals the provider’s ScopeClaim refuses startup, because such a claim is always present or means something else and would switch the requirement off.
(4) authorization_servers lists each identity provider’s Issuer. An Issuer must be an absolute https URI, the same rule as Authority, since clients are sent to it.
(5) Startup checks every File entry under Serilog:WriteTo, resolving its path the way the sink does, against the working directory, and refuses naming the resolved path if it cannot write there. Serilog’s self-log goes to stderr, so a sink that fails later says so.
G-13 challenge(UC-9) Docs profile: docs/04’s production configuration and compose file run verbatim through a declared substitution table. The table has two kinds of row: host names and addresses (identity provider, resource, proxy), and test-trust additions (SSL_CERT_* and the read-only CA mount), each with its reason. For that run the image is tagged with the name the compose file uses.
G-14 challenge(UC-1, 12) CI.
• Jobs: a separate end-to-end job on ubuntu-latest, running in parallel with the fast job on every push. The fast job runs McpServerTemplate.Tests by project path.
• Budget: the wall-clock budget is the walking skeleton’s measured job time plus a stated margin, and counts the confirmation-expiry wait. It is recorded on the contract before T-2 onward are written. Exceeding it fails the job and puts reshaping to the pioneer.
• Failures: a diagnostics bundle (container logs, journals, timings) is uploaded, and a hang timeout applies.
G-15 challenge(UC-2, 8) Closing contract-003. Each clause of its T-3, T-5 and T-10 maps to the test that closes it (table below). T-10’s first sentence (test server and program install the same frame) stays closed by the fast suite’s existing comparison, which this contract does not move.
G-16 challenge(UC-6; the bearing) Four named extension points, each one type in the harness: start a server with a settings delta; the upstream registry; the issuer registry; the network constant. Later contracts add through them. For example, egress puts a fault proxy in front of an upstream by registering it in place of the fake.
G-17 as drawn(UC-13) Adversarial rounds after the build, one lens each: the security of the fixes, the honesty of the harness, containment of the test image, flakiness on both platforms, and docs against behaviour. Confirmed findings are fixed with a test each. Rounds repeat until one finds nothing new, and every round’s findings are recorded on the contract.

Novel to the kit, so observations are due after the build: G-9 (a front that stands in for many clients), G-10 (containment by identity, not environment name), G-11 (sabotage must fail the claim’s own assertion), G-16 (extension points named in the contract).

The gate

What the gate asked

Disappointment: for any guarantee, what result would make you say it was not met? “Same as it says” is an answer.

Pre-mortem: imagine this contract built and passing, and the frame still failing somewhere later. What went wrong? At the last gate you said: “Pre mortem is if there are holes or security issues as a result of our work here.” If that stands for this contract too, say so.

Approval authorises building exactly these clauses. A deviation found in flight stops the work and comes to you. After the build, one guarantee is broken on purpose and the test that goes red is recorded before the contract reads implemented; then the adversarial rounds run until one finds nothing new.
