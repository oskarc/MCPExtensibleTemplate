Every Decision on the Record

Today the server can refuse a request and leave only a line of text, allow a resource read and leave nothing, and go on serving when its log cannot be written. This contract makes every decision a record that is written before the decision takes effect.

Direction

After this contract, nothing the frame governs takes effect before the decision that let it through, or refused it, is on a record an operator can check: one line per decision, attributed to the caller, chained so that a changed line is found by the server’s own check. The bet is that writing the record first, and refusing the act when the record cannot be written, is worth one flushed write per request, and that a chained file plus a background copy to a collector is enough of a trail without a keyed signature.

Everything below is derived from that. If a clause and the direction disagree, the clause is wrong.

How one request is recorded

How the file is chained and checked

Tier 1 — who it is for

Who. The people who run the server for an organisation and its security team; an investigator after an incident; the pioneer judging whether the frame holds; and the next phase, which takes access away on the strength of these records.

What they want. To answer, for any request, who made it, what it asked for, whether it was let through and by which rule, from a record they can trust; and to be told when the record itself has stopped.

Success. Every request leaves one line. A change is never made before its line is written. A line someone alters is found by a check the server ships. No line carries a secret. The lines use the vocabulary a security monitoring system already knows, with alerts ready.

Cost today. Refusals are text lines in the ordinary log. An allowed tool call leaves a text line; an allowed resource read, prompt or completion leaves none. No line names the token or the trace it belongs to. Any line can be edited unnoticed. If the log cannot be written, the server serves on.

Tier 2 — use cases

Use case
UC-1Every request leaves one record. A tool call, a resource read, a prompt, a completion, a list, sign-on, discovery, ping, a notification, a kind nobody governs: each leaves exactly one decision record — allowed, refused, or asked to confirm. A request rejected before any check still leaves one. An answer withheld after the tool ran is a second decision and a second record.
UC-2The record says who and what. Time, application id, event name, level, description, the caller (identity provider, subject, client, a hash of the token’s id, scopes — never the token), the method, provider, target, risk, the decision and its rule, the arguments with secrets removed, trace id, request id, source address, host name, request URI and method, user agent. Over stdio the HTTP facts are empty; a refusal before sign-in has no caller.
UC-3Record first; refuse when it cannot be written. An allowed request’s record is flushed before anything runs. If it cannot be written, a Write or Irreversible tool is refused and the server says the trail is down; every other request follows Audit:ReadWhenUnavailable, default deny. A refusal whose record cannot be written is still a refusal. The server recovers by itself.
UC-4A chain an operator can check. One file per server instance per day; each line carries the hash of the line before, its own hash and a running number. --verify-audit names the first line that breaks. The chain continues across midnight; files past the retention are removed.
UC-5Nothing secret, nothing forged. A sensitive argument becomes a short hash tag; a value shaped like a credential is always replaced; a long string is cut and carries a hash of the whole. A line break or escape character a caller sends cannot start a new line. A sensitive name the tool does not declare stops startup.
UC-6One trace through. Each record carries the request’s trace id — the caller’s own when one is sent — and a request id; the server opens named spans for the request and the tool.
UC-7The server’s own life is on the trail. Started, with a hash of the build and of the installed frame; stopped cleanly; crashed; trail down.
UC-8The HTTP layer’s refusals too. A refused token, a refused origin, and the per-address limit.
UC-9A copy leaves the machine. When a collector is configured, each record is also sent there in the background. A failing collector never delays or refuses a request, and is reported. The file stays the record.
UC-10The ordinary log holds no argument values. The switch that wrote a tool call’s full arguments at Debug is removed.
UC-11Alerts ship with the repository: first use of a tool by a caller; many refusals in ten minutes; any prompt injection, token reuse, egress denial or revocation failure; the trail stopping, and a gap in the running number.
UC-12Audit settings are checked like every other. An unknown key, a bad value or a directory that cannot be written stops startup, naming it.

Decided at the draw, without the pioneer

Each of these would have been a question at a spec lock. Each is also in docs/deferred/phase-3-audit.md with what overturning it would cost.

ChoiceWhy
1The tool-call event is written when the call is admitted, not when it completes, as the roadmap words it.A record written after the act leaves a moment in which an irreversible act has happened with no record. How the call ended stays in the ordinary log, joined by the trace id.
2A failing collector does not refuse requests; a failing file does.The file is the record, the collector a copy. Tying every write to a remote system’s uptime is a choice the pioneer should make knowingly.

Tier 4 — acceptance tests

No disappointment line and no pre-mortem were asked: the gate was waived. The tests were drafted against the standing answer the pioneer gave for the two contracts before this one: “Pre mortem is if there are holes or security issues as a result of our work here.”

CoversWhat is checked, and what failure looks like
T-1G-1, 2Every rule the gate can refuse by is driven through a real client. Fails if any leaves other than exactly one record with that rule, the wrong event name or level, or if the tool ran. A rule in the source with no driver fails the test.
T-2G-2A mixed run of N requests of every kind leaves exactly N records, each naming its method, plus one for a withheld answer.
T-3G-3Every record carries every required field. Over HTTP with a real token the caller and HTTP facts are right, the token-id hash matches, and neither the token nor its id is anywhere in the file.
T-4G-2, 4With a trail that cannot write: a Write tool is refused and did not run, and the server says the trail is down; a read is refused by default and allowed when set so; once the trail accepts, the next write runs. When the “allowed” record is appended, the tool’s counter has not moved.
T-5G-5The real program’s --verify-audit passes a file the server wrote (exit 0) and names the exact line after a byte is flipped, a line removed, two swapped or the last cut short (exit 65); a missing file exits 66.
T-6G-5Across midnight on a test clock the chain continues into a new file and both verify in order; files past the retention are gone and newer ones kept.
T-7G-6, 7A sensitive argument, a token-shaped value at any depth and a 10 KB string each come out as specified. CR, LF and ESC in a tool name, an argument and a user agent leave exactly as many lines as records, each valid JSON. An undeclared sensitive name stops startup.
T-8G-8A request sent with a trace header has that trace id in its record, and code inside the tool sees the same; a listener observes a request span and a tool span.
T-9G-9The real program, started and stopped: started is the first record and carries the hash of the server’s own file, stopped is the last, and the file verifies. A bare composition leaves no file.
T-10G-10A foreign origin, an unregistered issuer and an expired token each leave one record with no caller and no token text; the 61st request from one address in a minute leaves one.
T-11G-11Each record reaches an in-process collector with the same line as the file’s. With the collector failing, requests are unaffected and the file is complete. A plain-http or credential-carrying endpoint stops startup, and the credential is in no output.
T-12G-12An unknown audit key, an unwritable directory, a bad mode and a zero retention each stop startup, naming it.
T-13G-13A marker value sent as an argument with the log at Debug appears in no ordinary log line; the line naming the arguments is still there.
T-14G-14Every alert file parses, names only events the server can emit, and the roadmap’s four cases each have one.
T-15G-1With the installed filters tampered so the audit step is not first, or the request-kind gate not second, startup refuses and says which.

Boundaries

  • It does not take access away. Strikes, suspension and revocation are Phase 4, and read these records.
  • It does not scan tool output for hostile instructions. The roadmap moved that to Phase 4.
  • It does not define the outbound guard’s refusals or the tool lock’s. Those contracts are being drawn by two other sessions; this one gives them the event and the one call that records it.
  • It does not prove a file was not rewritten whole. That needs the copy outside the machine compared, or a keyed signature.
  • It does not touch the Dockerfile, add a package, or change a log line or a reply that exists today.
  • It is not shown on the shipped image. Those tests are owed.
